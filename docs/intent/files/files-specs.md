# Complete files specs

Design: [files-design.md](files-design.md). Prefix `ING`, facets FILE, HTTP.

## Capability, route and gate (FILE)

- [ ] **ING-FILE-075**: When core's `POST /v1/audio/transcriptions` is registered, `attach_router` shall add the frontend's file route `POST /plugins/riva/v1/audio/transcriptions` beside it, leaving core's route registered and unchanged; when core's route is absent, `attach_router` shall add no file route; the frontend shall serve no translation route and shall not mount, replace or shadow `POST /v1/audio/translations`; and every requirement on the frontend's file route binds only `POST /plugins/riva/v1/audio/transcriptions`, every requirement on a file request or file owner binds only `Recognize` and that route, and neither binds core's `POST /v1/audio/transcriptions`, which ING-FILE-076 leaves to core.
- [ ] **ING-FILE-076**: The frontend shall leave core's `POST /v1/audio/transcriptions` with core's behaviour whether or not complete files are enabled on the frontend, applying none of its ingress cap, file gate, guard or memory bound to that route, whose traffic the frontend's gate sizing (ING-FILE-009) does not count.
- [x] **ING-FILE-014**: `Recognize` and the frontend's file route shall require the model's `transcription` task, and without `state.openai_serving_transcription` `Recognize` shall answer `UNIMPLEMENTED`.
- [x] **ING-FILE-015**: `init_state` shall derive one files-enabled flag, true when `state.openai_serving_transcription` is present and the gate sizing allows files, and that flag alone shall decide `Recognize`'s capability and the `type=offline` listing of the configuration RPC.
- [x] **ING-FILE-016**: When `min(slots, active limit)` is below 2 and `max_concurrent_files` is not configured, `init_state` shall disable complete files with a startup warning, so that `Recognize` answers `UNIMPLEMENTED` and no `offline` entry is listed.
- [ ] **ING-FILE-083**: While files are disabled and core's transcription service is present, the frontend's file route `POST /plugins/riva/v1/audio/transcriptions` (which `attach_router` registered before `init_state` sized the gate) shall refuse every request with `unsupported_capability` projected as HTTP 501 as its first step, before the ingress cap and before reading a body, creating no owner.
- [x] **ING-FILE-018**: If core's transcription service is present and `max_concurrent_files` is configured and is not below both the state-slot count and the active-request limit, then `init_state` shall fail startup.
- [ ] **ING-FILE-080**: One counting gate of `max_concurrent_files` shall cover `Recognize` and the frontend's file route (files sent to core's own `POST /v1/audio/transcriptions` are outside it), waiters shall wait in the frontend as owner tasks, a permit shall be held until the response body has been sent (for `Recognize`, until the response is returned) and the owner's children have settled, and then released exactly once by the owner or its cleanup continuation (ING-FILE-079), and the gate shall cap the frontend's files in flight without reserving stream capacity.
- [x] **ING-FILE-009**: While complete files are enabled, `max_concurrent_files` shall be below both the state-slot count and the engine's active-request limit (ING-EP-030).
- [x] **ING-FILE-019**: When a gate wait exceeds `file_gate_wait_timeout`, the request shall answer `busy` with `authority: load_shed`.
- [x] **ING-FILE-053**: When the plugin is draining, the gate shall refuse new waiters.
- [x] **ING-FILE-048**: When the plugin cancels a file request at shutdown, the frontend's file route shall answer `service_unavailable` with HTTP 503 before response headers, or terminate the event stream after them, and `Recognize` shall answer `UNAVAILABLE`.
- [ ] **ING-FILE-082**: When `drain` cancels a file request at its settle point (ING-EP-073), the handler shall answer `service_unavailable` at once (ING-FILE-048) and hand the whole cleanup to the request's cleanup continuation (ING-FILE-079), so that the client learns of the shutdown while the listener is still up.

## The request guard (FILE)

- [x] **ING-FILE-010**: The frontend's file route and `Recognize` shall refuse `use_beam_search` true and any `max_completion_tokens` with 400 or `INVALID_ARGUMENT` before taking a permit, and `Recognize` shall never set them.
- [x] **ING-FILE-020**: The frontend's file route shall refuse with 400 `invalid_config_field` naming the field any explicit non-default value of `temperature`, `top_p`, `top_k`, `min_p`, `frequency_penalty`, `presence_penalty`, `repetition_penalty`, `seed` or `watermarking`, where core's defaults are 0 for `temperature`, `frequency_penalty` and `presence_penalty`, 1 for `top_p` and `repetition_penalty`, 0 for `top_k` and `min_p`, and absent for `seed` and `watermarking`.
- [x] **ING-FILE-021**: The guard shall accept an omitted field and an explicit value equal to core's default, shall refuse an explicit non-default value, and shall not inspect the effective value a field inherits from the served model's generation settings.
- [x] **ING-FILE-022**: The frontend's file route shall refuse with 400 `invalid_config_field` before taking a permit an explicit `n` other than 1, `length_penalty` other than 1.0 and `include_stop_str_in_output` true, and shall pass `prompt`, `hotwords` and `to_language` to core for its own 400.
- [x] **ING-FILE-023**: The frontend's file route shall validate its text parts against an explicit allowlist of the field names and aliases of core's `TranscriptionRequest` (including `timestamp_granularities[]`) and refuse any other part with 400 `invalid_config_field` naming it, and a test shall fail when core adds or renames a field.
- [x] **ING-FILE-054**: When core's transcription service is present and the served model's generation settings carry a guarded sampling key, `init_state` shall log a warning.
- [x] **ING-FILE-024**: The frontend's file route shall accept a client `vllm_xargs` only when it contains the single key `locale`, validate that value against the factory's `locales` (`unknown_locale`, 400) and forward it as given, and shall refuse any other key with 400.

## Locale (FILE)

- [x] **ING-FILE-025**: The frontend's file route shall forward the client's `language` field to core unchanged, and shall not apply exact-locale transport.
- [x] **ING-FILE-013**: `Recognize` shall validate its `language_code` (or `default_locale` when empty) against the factory's `locales` and send it exactly as `vllm_xargs={"locale": <locale>}`, shall set `language` to the locale's language (ING-FILE-085) only when that language is in the model's `supported_languages` and otherwise `None` (also for `auto`), and when `default_locale` is `None` and the client names none shall answer `invalid_config_field` naming `language_code`.

## Request ID, ownership and accounting (FILE)

- [x] **ING-FILE-026**: The frontend's file route shall fix the engine request ID by passing core a new `Request` built over a copy of the original scope with every client `x-request-id` header removed and a frontend-generated UUID added, so that the engine request ID is `transcribe-<uuid>`, and shall not mutate the original request.
- [x] **ING-FILE-027**: `Recognize` shall fix its engine request ID with a minimal synthetic `Request` whose scope carries only an `x-request-id` header holding a frontend-generated UUID.
- [x] **ING-FILE-067**: The owner of a file request (to `Recognize` or the frontend's file route) shall record exactly one terminal cause at its operation boundaries (the permit, the return of core's service call, each pull of core's event generator and each response send): a client disconnect or RPC cancellation observed before any cause is selected shall win and produce no response; otherwise the first of shutdown, a deadline (ING-ERR-056) or a failure recorded there shall stay primary and decide the response; a disconnect observed after a cause was selected shall suppress the response and leave the recorded cause unchanged; and a later abort, close or settlement failure shall never change the response.
- [x] **ING-FILE-068**: A file request (to `Recognize` or the frontend's file route) shall pass these milestones: the permit; the return of core's service call once core's preprocessing is done, which for `stream=true` returns an event generator; the exhaustion of that generator (`stream=true` only); and the delivery of the response. When a cause is selected after the permit and before the service call has returned or, for `stream=true`, before the generator is exhausted, the owner shall call the engine client's `abort` for the engine request ID and repeat it every 250 ms until the service call has returned and, for `stream=true`, any outstanding pull of the generator has finished, and then shall send one final awaited `abort` for that ID before closing the generator and before releasing any accounting, because core submits the request lazily and an earlier abort can miss it; when a cause is selected before the permit or after that point, the owner shall instead follow ING-FILE-007 and call no `abort`.
- [x] **ING-FILE-069**: The owner of a file request (to `Recognize` or the frontend's file route) alone shall advance core's event generator, one pull at a time with no overlapping pulls, and when a cause is selected shall close the generator with `aclose`, after the final awaited `abort` of ING-FILE-068 when that spec requires an abort, and with no `abort` when the cause is selected after the generator is exhausted.
- [ ] **ING-FILE-077**: The owner of a file request (to `Recognize` or the frontend's file route) shall never cancel core's service call, in `drain` and `stop` alike, ending the engine request only through the engine client's `abort` (ING-FILE-068), and shall not treat closing core's outer generator, or cancelling the child that made the call, as ending the engine request.
- [ ] **ING-FILE-078**: The cleanup deadline of a file owner (of `Recognize` or the frontend's file route) shall start when the cause is selected and shall cover the abort retries, the final awaited `abort`, the cancellation of the disconnect watcher, the closing of the event generator and the settlement of the owner's children, bounded by `session_cleanup_timeout`, except that while a frontend `drain` call is running and its drain deadline `D` has not passed the bound shall be the smaller of that and the time left to `D` (while the plugin is draining with no `drain` call, ING-EP-102, it is `session_cleanup_timeout` unclipped), and in the vehicle's settlement after `D` (ING-EP-093) it shall be `session_cleanup_timeout` from the moment the settlement cancels the owner; when that bound expires the handler may answer and shall hand the remaining cleanup to the cleanup continuation of ING-FILE-079, and the expiry shall not be taken to mean the children settled.
- [ ] **ING-FILE-079**: The cleanup of a file request (to `Recognize` or the frontend's file route) shall be owned by a cleanup continuation registered in the owner registry, which owns the abort retries, the final awaited `abort`, the closing of the event generator, the settlement of the children and the exactly-once release of the permit, the file-owner slot and the server-load count; when the handler answers before settlement it shall transfer that ownership to the continuation; the registry record shall persist until the continuation's last step; and the vehicle's settlement in `drain` and in `stop` (ING-EP-093) shall cancel the owner and await the continuation through that cancellation, the continuation still completing its abort retries, final abort, children's settlement and accounting release.
- [x] **ING-FILE-007**: A client disconnect before the permit is taken shall discard only multipart memory, a disconnect after the service completed normally and during the response send shall suppress the response only, and no successful response shall be emitted after a disconnect, cancellation, shutdown or timeout during body read, validation or core's execution.
- [x] **ING-FILE-072**: When `enable_server_load_tracking` is set, the owner of a request to the frontend's file route shall increment `server_load_metrics` when admitted, the owner or its cleanup continuation (ING-FILE-079) shall decrement it exactly once after settlement and after the response send finished or failed, and the route shall not use core's `load_aware_call`.
- [x] **ING-FILE-049**: `Recognize` shall not be counted in the server-load counter.
- [x] **ING-FILE-064**: For `Recognize` and the frontend's file route, `file_execution_timeout` shall be an absolute deadline from the permit to the return of core's service call, or for `stream=true` to the exhaustion of core's event generator, for `stream=true` that deadline includes delivery pacing because pulls wait on sends, its expiry shall be `request_timeout`, and delivery after that point shall be bounded only by `response_send_timeout` for each send (ING-FILE-073).
- [x] **ING-FILE-065**: For `Recognize`, the RPC's absolute deadline shall apply from servicer entry through request validation, the gate wait and execution, and where it and another deadline both apply the deadline precedence rule (ING-ERR-056) shall decide which wins.
- [x] **ING-FILE-035**: Before response headers are sent, a failure of the frontend's file route shall be an HTTP error in core's shape, and after headers are sent a failure shall end the event stream with core's streaming error event shape when it can be serialized or close the connection, and shall never send an HTTP status.
- [x] **ING-FILE-073**: The frontend's file route shall bound each response send by `response_send_timeout`, and a reader that stalls longer shall be cancelled; while core's service call is executing or, for `stream=true`, its event generator is not exhausted (ING-FILE-068), the engine request shall be aborted, after the service completed normally delivery shall be suppressed with no `abort`, and in both cases the permit shall be released after settlement.
- [x] **ING-FILE-066**: After the guard and the permit, the frontend's file route shall call core's transcription service with the audio bytes and return core's response, event stream or returned `ErrorResponse` as core's route does, and shall pass core's raised exceptions through by re-raising them from the route handler, so that core's application exception handlers shape them.

## HTTP route ingress (FILE, HTTP)

- [x] **ING-FILE-055**: The frontend's file route shall run its steps in this order: files-enabled check (ING-FILE-083), ingress cap, content type, body read, parse, validate and guard, gate permit, call to core.
- [x] **ING-FILE-004**: The frontend's file route shall consume raw ASGI body chunks directly through `python-multipart.MultipartParser` callbacks, shall not call `request.form()`, use a file-object `FormParser` or invoke any framework or helper permitted to spool, shall keep the one file part and the bounded text fields only in application-owned memory, and filename, boundary and part content type shall remain untrusted metadata never used as a path or persisted.
- [x] **ING-FILE-005**: The frontend's file route shall require `multipart/form-data` with exactly one syntactically valid bounded ASCII boundary, and shall answer `malformed_request` with HTTP 400 for JSON, URL-encoded forms, a missing or duplicate boundary parameter, malformed or non-ASCII boundary syntax, malformed framing, truncated input, a duplicate field (other than a repeated field core declares as a list, ING-FILE-042), a second file or a missing file.
- [x] **ING-FILE-039**: When a request body exceeds `http_multipart_envelope_max_bytes`, or a syntactically valid `Content-Type` or boundary exceeds its byte cap, the frontend's file route shall answer `request_too_large` with HTTP 413 before core is called.
- [x] **ING-FILE-037**: The frontend's file route shall feed each body chunk to the parser as it arrives and shall not retain the encoded body whole.
- [x] **ING-FILE-038**: When the total body read time exceeds `http_body_read_timeout`, the frontend's file route shall answer `request_timeout` with HTTP 408.
- [x] **ING-FILE-006**: When core's transcription service is present, `init_state` shall require a finite positive `http_multipart_envelope_max_bytes` that is at least `VLLM_MAX_AUDIO_CLIP_FILESIZE_MB` MiB plus 262,144 bytes of framing allowance, and shall fail startup otherwise.
- [x] **ING-HTTP-007**: While parsing the multipart input of the frontend's file route, the handler shall enforce total bytes, part count, part-header bytes, text-field bytes and file bytes before extending their buffers, a present `Content-Length` above the complete-body limit (`http_multipart_envelope_max_bytes`) shall reject before the body is read, a missing or chunked length shall remain supported under the same running limit, every ASGI chunk fragmentation including boundary splits shall parse equivalently, and parser truncation or disconnect shall never become success and shall discard only bounded in-memory state.
- [x] **ING-FILE-041**: The frontend's file route shall build the upload object handed to core from the parsed file part as an in-memory `BytesIO`-backed upload, without copying the part buffer and without spooling.
- [x] **ING-FILE-042**: The frontend's file route shall validate the text parts with core's `TranscriptionRequest` model, allow a repeated name only for a field core declares as a list, and answer `malformed_request` for any other duplicate.
- [x] **ING-FILE-011**: The frontend's file route shall apply core's upload limit (`VLLM_MAX_AUDIO_CLIP_FILESIZE_MB`) to the file part by running it through core's `read_upload_with_limit`.
- [x] **ING-HTTP-011**: The request path of the frontend's file route shall write no audio, multipart bytes, decoded samples, boundary or filename to the filesystem and shall create no local spool or retained request-audio artifact on success, rejection, cancellation, disconnect, shutdown or failure; client fixture reads and test-result writes remain outside this prohibition.

## `Recognize` (FILE)

- [x] **ING-FILE-001**: `Recognize` shall be wire-unary: after request validation (ING-FILE-002) it shall convert the request's audio to an in-memory 16 kHz mono 16-bit WAV, take a file-gate permit, call core's transcription service with those bytes, the exact locale (ING-FILE-013), `response_format` `json`, no streaming, no beam search and no completion limit, and return one `RecognizeResponse` only after the service completes normally; it shall use no session factory, no full-context algorithm of its own and no second segmenter.
- [x] **ING-FILE-045**: `Recognize` shall return one result with one alternative carrying the transcript, with an empty transcript when the text is empty; the result's `audio_processed` shall be the duration of the WAV handed core (its frame count divided by 16000), and the alternative shall carry no `confidence`.
- [x] **ING-FILE-002**: Before taking a file-gate permit, `Recognize` shall validate the complete format, locale, encoded-request bound, RIFF-header bound and decoded-duration bound, and at each validation, permit and terminal boundary a cancellation or an already-expired RPC deadline already observed shall win over the specific validation error.
- [x] **ING-FILE-046**: When core's transcription service is present, `init_state` shall fail startup when `unary_max_decoded_duration_seconds` exceeds core's `VLLM_MAX_AUDIO_DECODE_DURATION_S`.
- [ ] **ING-FILE-081**: The frontend shall add no startup relation between its duration caps (`unary_max_decoded_duration_seconds` and core's decode-duration limit) and `max_model_len`, shall project no length refusal for a file, and shall inspect no finish reason of core's transcription result, leaving `--max-model-len` to the deployment guide's sizing (ING-EP-078).
- [x] **ING-FILE-050**: `Recognize` shall treat a returned `ErrorResponse` and a raised exception from core's service as separate failure kinds and project each as the errors leaf defines.
- [x] **ING-FILE-043**: The peak frontend audio memory of a file owner (of `Recognize` or the frontend's file route) shall not exceed the configuration-derived bound of the files design (route: `3 x http_multipart_envelope_max_bytes`, counting the parsed file part, the upload object and core's joined bytes; `Recognize`: `unary_max_encoded_audio_bytes + 6 x 16000 x unary_max_decoded_duration_seconds + 44` bytes plus a 4 MiB slice allowance, counting the encoded request, the decoded `float32` samples, the resampler's slice state and temporaries and the WAV), excluding core's decode memory; at the default configuration a test shall measure each path's peak under 128 MiB, as the increase in `tracemalloc`'s traced peak over the pre-request baseline for one maximal request with core's service replaced by a stub that reads the bytes and returns a transcript.
- [x] **ING-FILE-044**: The samples `Recognize` hands core (the WAV of ING-FE-008, decoded) shall equal the samples the stream side hands `feed` for the same audio after the requantization of ING-FE-012, and the frontend shall send core exactly the locale a stream opened with the same client locale would use (ING-FILE-013, ING-CORE-015).
- [x] **ING-FILE-056**: For a file whose request ends with EOS and a comparison session that is flushed successfully, with a fixed locale (no `update_locale`), the same samples (ING-FILE-044), a comparison session opened at the cadence core's file path uses (the deployment guide's `num_lookahead_tokens`, ING-EP-078), the same precision settings and endpointing disabled on both, an integration test shall find the file's transcript equal to the session's final transcript; transcript equality is the string projection of the label-sequence equality the model plugin's FILE-ROW-007 states.
- [x] **ING-FILE-057**: A contract test shall build core's `TranscriptionRequest.to_sampling_params` result and fail when it sets a sampling parameter from a request field that the guard does not handle (the fields of ING-FILE-020, the completion limit of ING-FILE-010 and `vllm_xargs` of ING-FILE-024).
- [x] **ING-FILE-058**: A CPU test shall decode the WAV of ING-FE-008 through core's audio decoder and fail unless the decoded samples equal the WAV's 16-bit values divided by 32768.
- [ ] **ING-FILE-084**: Contract tests that run against core's code shall pin each part of core's transcription service the frontend uses (the `state.openai_serving_transcription` attribute that core's state construction builds, `create_transcription(audio, request, raw_request)`, the `TranscriptionRequest` model, `read_upload_with_limit`, core's derivation of the engine request ID from the request, and the engine client's `abort`) and shall fail when core changes any of them, including a test that a client-supplied `X-Request-Id` does not reach core; and a test in the model plugin repository's seam conformance run, on the RFC 1 + RFC 2 build, shall pin the single-engine-input assumption that the served model declares `max_audio_clip_s=None` and no explicit language detection, so that core issues no chunk or language-detection request under another request ID.
- [ ] **ING-FILE-085**: For `Recognize`, a locale's language shall be the characters of the locale name before its first `-` or uppercase letter (the whole name when it has neither) when they are two or three lowercase ASCII letters, and the locale shall have no language otherwise (`auto` among them), and a test in the model plugin repository's seam conformance run, on the RFC 1 + RFC 2 build, shall pin this rule against the model plugin's own locale-language definition.
