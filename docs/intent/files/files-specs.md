# Complete files specs

Design: [files-design.md](files-design.md). Prefix `ING`, facets FILE, HTTP.

## Capability, route and gate (FILE)

- [x] **ING-FILE-003**: When core's `POST /v1/audio/transcriptions` route is present, `attach_router` shall replace it with the frontend's file route (RFC 2 route override); when it is absent, `attach_router` shall replace nothing; and the frontend shall not mount, replace or shadow `POST /v1/audio/translations`.
- [x] **ING-FILE-014**: `Recognize` and the file route shall require the model's `transcription` task, and without `state.openai_serving_transcription` `Recognize` shall answer `UNIMPLEMENTED`.
- [x] **ING-FILE-015**: `init_state` shall derive one files-enabled flag, true when `state.openai_serving_transcription` is present and the gate sizing allows files, and that flag alone shall decide `Recognize`'s capability and the `type=offline` listing of the configuration RPC.
- [x] **ING-FILE-016**: When `min(slots, active limit)` is below 2 and `max_concurrent_files` is not configured, `init_state` shall disable complete files with a startup warning, so that `Recognize` answers `UNIMPLEMENTED` and no `offline` entry is listed.
- [x] **ING-FILE-017**: While files are disabled and the service is present, the file route shall refuse every request with `unsupported_capability` projected as HTTP 501 as its first step, before the ingress cap and before reading a body, creating no owner.
- [x] **ING-FILE-018**: If core's transcription service is present and `max_concurrent_files` is configured and is not below both the state-slot count and the active-request limit, then `init_state` shall fail startup.
- [x] **ING-FILE-074**: One counting gate of `max_concurrent_files` shall cover `Recognize` and the file route, waiters shall wait in the frontend as owner tasks, a permit shall be held until the response body has been sent (for `Recognize`, until the response is returned) and the owner's children have settled, and then released exactly once by the owner or its cleanup continuation (ING-FILE-071), and the gate shall cap files in flight without reserving stream capacity.
- [x] **ING-FILE-009**: While complete files are enabled, `max_concurrent_files` shall be below both the state-slot count and the engine's active-request limit (ING-EP-030).
- [x] **ING-FILE-019**: When a gate wait exceeds `file_gate_wait_timeout`, the request shall answer `busy` with `authority: load_shed`.
- [x] **ING-FILE-053**: When the plugin is draining, the gate shall refuse new waiters.
- [x] **ING-FILE-048**: When the plugin cancels a file request at shutdown, the route shall answer `service_unavailable` with HTTP 503 before response headers, or terminate the event stream after them, and `Recognize` shall answer `UNAVAILABLE`.

## The request guard (FILE)

- [x] **ING-FILE-010**: The file route and `Recognize` shall refuse `use_beam_search` true and any `max_completion_tokens` with 400 or `INVALID_ARGUMENT` before taking a permit, and `Recognize` shall never set them.
- [x] **ING-FILE-020**: The file route shall refuse with 400 `invalid_config_field` naming the field any explicit non-default value of `temperature`, `top_p`, `top_k`, `min_p`, `frequency_penalty`, `presence_penalty`, `repetition_penalty`, `seed` or `watermarking`, where core's defaults are 0 for `temperature`, `frequency_penalty` and `presence_penalty`, 1 for `top_p` and `repetition_penalty`, 0 for `top_k` and `min_p`, and absent for `seed` and `watermarking`.
- [x] **ING-FILE-021**: The guard shall accept an omitted field and an explicit value equal to core's default, shall refuse an explicit non-default value, and shall not inspect the effective value a field inherits from the served model's generation settings.
- [x] **ING-FILE-022**: The file route shall refuse with 400 `invalid_config_field` before taking a permit an explicit `n` other than 1, `length_penalty` other than 1.0 and `include_stop_str_in_output` true, and shall pass `prompt`, `hotwords` and `to_language` to core for its own 400.
- [x] **ING-FILE-023**: The file route shall validate its text parts against an explicit allowlist of the field names and aliases of core's `TranscriptionRequest` (including `timestamp_granularities[]`) and refuse any other part with 400 `invalid_config_field` naming it, and a test shall fail when core adds or renames a field.
- [x] **ING-FILE-054**: When core's transcription service is present and the served model's generation settings carry a guarded sampling key, `init_state` shall log a warning.
- [x] **ING-FILE-024**: The file route shall accept a client `vllm_xargs` only when it contains the single key `locale`, validate that value against the factory's `locales` (`unknown_locale`, 400) and forward it as given, and shall refuse any other key with 400.

## Locale (FILE)

- [x] **ING-FILE-025**: The file route shall forward the client's `language` field to core unchanged, and shall not apply exact-locale transport.
- [x] **ING-FILE-013**: `Recognize` shall validate its `language_code` (or `default_locale` when empty) against the factory's `locales` and send it exactly as `vllm_xargs={"locale": <locale>}`, shall set `language` to the locale's language only when that language is in the model's `supported_languages` and otherwise `None` (also for `auto`), and when `default_locale` is `None` and the client names none shall answer `invalid_config_field` naming `language_code`.

## Request ID, ownership and accounting (FILE)

- [x] **ING-FILE-026**: The file route shall fix the engine request ID by passing core a new `Request` built over a copy of the original scope with every client `x-request-id` header removed and a frontend-generated UUID added, so that the engine request ID is `transcribe-<uuid>`, and shall not mutate the original request.
- [x] **ING-FILE-027**: `Recognize` shall fix its engine request ID with a minimal synthetic `Request` whose scope carries only an `x-request-id` header holding a frontend-generated UUID.
- [x] **ING-FILE-067**: The owner of a file request shall record exactly one terminal cause at its operation boundaries (the permit, the return of core's service call, each pull of core's event generator and each response send): a client disconnect or RPC cancellation observed before any cause is selected shall win and produce no response; otherwise the first of shutdown, a deadline (ING-ERR-056) or a failure recorded there shall stay primary and decide the response; a disconnect observed after a cause was selected shall suppress the response and leave the recorded cause unchanged; and a later abort, close or settlement failure shall never change the response.
- [x] **ING-FILE-068**: A file request shall pass these milestones: the permit; the return of core's service call once core's preprocessing is done, which for `stream=true` returns an event generator; the exhaustion of that generator (`stream=true` only); and the delivery of the response. When a cause is selected after the permit and before the service call has returned or, for `stream=true`, before the generator is exhausted, the owner shall call the engine client's `abort` for the engine request ID and repeat it every 250 ms until the service call has returned and, for `stream=true`, any outstanding pull of the generator has finished, and then shall send one final awaited `abort` for that ID before closing the generator and before releasing any accounting, because core submits the request lazily and an earlier abort can miss it; when a cause is selected before the permit or after that point, the owner shall instead follow ING-FILE-007 and call no `abort`.
- [x] **ING-FILE-069**: The owner of a file request alone shall advance core's event generator, one pull at a time with no overlapping pulls, and when a cause is selected shall close the generator with `aclose`, after the final awaited `abort` of ING-FILE-068 when that spec requires an abort, and with no `abort` when the cause is selected after the generator is exhausted.
- [x] **ING-FILE-029**: Apart from the cancellation of unsettled children by `stop` (ING-FILE-071), the owner of a file request shall never cancel core's service call, and shall not treat closing core's outer generator as ending the engine request.
- [x] **ING-FILE-070**: A file owner's cleanup deadline shall start when the cause is selected and shall cover the abort retries, the final awaited `abort`, the cancellation of the disconnect watcher, the closing of the event generator and the settlement of the owner's children, bounded by `session_cleanup_timeout` (the smaller of that and the time left to the drain deadline while draining); when that bound expires the handler may answer and shall hand the remaining cleanup to the cleanup continuation of ING-FILE-071, and the expiry shall not be taken to mean the children settled.
- [x] **ING-FILE-071**: A file request's cleanup shall be owned by a cleanup continuation registered in the owner registry, which owns the abort retries, the final awaited `abort`, the closing of the event generator, the settlement of the children and the exactly-once release of the permit, the file-owner slot and the server-load count; when the handler answers before settlement it shall transfer that ownership to the continuation, the registry record shall persist until the continuation's last step, and `stop` shall cancel the continuation and the children it holds (ING-EP-059).
- [x] **ING-FILE-007**: A client disconnect before the permit is taken shall discard only multipart memory, a disconnect after the service completed normally and during the response send shall suppress the response only, and no successful response shall be emitted after a disconnect, cancellation, shutdown or timeout during body read, validation or core's execution.
- [x] **ING-FILE-072**: When `enable_server_load_tracking` is set, the file route's owner shall increment `server_load_metrics` when admitted, the owner or its cleanup continuation (ING-FILE-071) shall decrement it exactly once after settlement and after the response send finished or failed, and the route shall not use core's `load_aware_call`.
- [x] **ING-FILE-049**: `Recognize` shall not be counted in the server-load counter.
- [x] **ING-FILE-064**: For `Recognize` and the file route, `file_execution_timeout` shall be an absolute deadline from the permit to the return of core's service call, or for `stream=true` to the exhaustion of core's event generator, for `stream=true` that deadline includes delivery pacing because pulls wait on sends, its expiry shall be `request_timeout`, and delivery after that point shall be bounded only by `response_send_timeout` for each send (ING-FILE-073).
- [x] **ING-FILE-065**: For `Recognize`, the RPC's absolute deadline shall apply from servicer entry through request validation, the gate wait and execution, and where it and another deadline both apply the deadline precedence rule (ING-ERR-056) shall decide which wins.
- [x] **ING-FILE-035**: Before response headers are sent, a failure of the file route shall be an HTTP error in core's shape, and after headers are sent a failure shall end the event stream with core's streaming error event shape when it can be serialized or close the connection, and shall never send an HTTP status.
- [x] **ING-FILE-073**: The file route shall bound each response send by `response_send_timeout`, and a reader that stalls longer shall be cancelled; while core's service call is executing or, for `stream=true`, its event generator is not exhausted (ING-FILE-068), the engine request shall be aborted, after the service completed normally delivery shall be suppressed with no `abort`, and in both cases the permit shall be released after settlement.
- [x] **ING-FILE-066**: After the guard and the permit, the file route shall call core's transcription service with the audio bytes and return core's response, event stream or returned `ErrorResponse` as core's route does, and shall pass core's raised exceptions through by re-raising them from the route handler, so that core's application exception handlers shape them.

## HTTP route ingress (FILE, HTTP)

- [x] **ING-FILE-055**: The file route shall run its steps in this order: files-enabled check (ING-FILE-017), ingress cap, content type, body read, parse, validate and guard, gate permit, call to core.
- [x] **ING-FILE-004**: The file route shall consume raw ASGI body chunks directly through `python-multipart.MultipartParser` callbacks, shall not call `request.form()`, use a file-object `FormParser` or invoke any framework or helper permitted to spool, shall keep the one file part and the bounded text fields only in application-owned memory, and filename, boundary and part content type shall remain untrusted metadata never used as a path or persisted.
- [x] **ING-FILE-005**: The file route shall require `multipart/form-data` with exactly one syntactically valid bounded ASCII boundary, and shall answer `malformed_request` with HTTP 400 for JSON, URL-encoded forms, a missing or duplicate boundary parameter, malformed or non-ASCII boundary syntax, malformed framing, truncated input, a duplicate field (other than a repeated field core declares as a list, ING-FILE-042), a second file or a missing file.
- [x] **ING-FILE-039**: When a request body exceeds `http_multipart_envelope_max_bytes`, or a syntactically valid `Content-Type` or boundary exceeds its byte cap, the file route shall answer `request_too_large` with HTTP 413 before core is called.
- [x] **ING-FILE-037**: The file route shall feed each body chunk to the parser as it arrives and shall not retain the encoded body whole.
- [x] **ING-FILE-038**: When the total body read time exceeds `http_body_read_timeout`, the file route shall answer `request_timeout` with HTTP 408.
- [x] **ING-FILE-006**: When core's transcription service is present, `init_state` shall require a finite positive `http_multipart_envelope_max_bytes` that is at least `VLLM_MAX_AUDIO_CLIP_FILESIZE_MB` MiB plus 262,144 bytes of framing allowance, and shall fail startup otherwise.
- [x] **ING-HTTP-007**: While parsing the file route's multipart input, the handler shall enforce total bytes, part count, part-header bytes, text-field bytes and file bytes before extending their buffers, a present `Content-Length` above the complete-body limit (`http_multipart_envelope_max_bytes`) shall reject before the body is read, a missing or chunked length shall remain supported under the same running limit, every ASGI chunk fragmentation including boundary splits shall parse equivalently, and parser truncation or disconnect shall never become success and shall discard only bounded in-memory state.
- [x] **ING-FILE-041**: The file route shall build the upload object handed to core from the parsed file part as an in-memory `BytesIO`-backed upload, without copying the part buffer and without spooling.
- [x] **ING-FILE-042**: The file route shall validate the text parts with core's `TranscriptionRequest` model, allow a repeated name only for a field core declares as a list, and answer `malformed_request` for any other duplicate.
- [x] **ING-FILE-011**: The file route shall apply core's upload limit (`VLLM_MAX_AUDIO_CLIP_FILESIZE_MB`) to the file part by running it through core's `read_upload_with_limit`.
- [x] **ING-HTTP-011**: The file route's request path shall write no audio, multipart bytes, decoded samples, boundary or filename to the filesystem and shall create no local spool or retained request-audio artifact on success, rejection, cancellation, disconnect, shutdown or failure; client fixture reads and test-result writes remain outside this prohibition.

## `Recognize` (FILE)

- [x] **ING-FILE-001**: `Recognize` shall be wire-unary: after request validation (ING-FILE-002) it shall convert the request's audio to an in-memory 16 kHz mono 16-bit WAV, take a file-gate permit, call core's transcription service with those bytes, the exact locale (ING-FILE-013), `response_format` `json`, no streaming, no beam search and no completion limit, and return one `RecognizeResponse` only after the service completes normally; it shall use no session factory, no full-context algorithm of its own and no second segmenter.
- [x] **ING-FILE-045**: `Recognize` shall return one result with one alternative carrying the transcript, with an empty transcript when the text is empty.
- [x] **ING-FILE-002**: Before taking a file-gate permit, `Recognize` shall validate the complete format, locale, encoded-request bound, RIFF-header bound and decoded-duration bound, and at each validation, permit and terminal boundary a cancellation or an already-expired RPC deadline already observed shall win over the specific validation error.
- [x] **ING-FILE-046**: When core's transcription service is present, `init_state` shall fail startup when `unary_max_decoded_duration_seconds` exceeds core's `VLLM_MAX_AUDIO_DECODE_DURATION_S`.
- [x] **ING-FILE-047**: When core's service raises the model's token-budget refusal for a `Recognize` file, `Recognize` shall project `request_too_large` with `RESOURCE_EXHAUSTED`, and the frontend shall add no startup relation between `unary_max_decoded_duration_seconds` and `max_model_len`.
- [x] **ING-FILE-050**: `Recognize` shall treat a returned `ErrorResponse` and a raised exception from core's service as separate failure kinds and project each as the errors leaf defines.
- [x] **ING-FILE-043**: A file owner's peak frontend audio memory shall not exceed the configuration-derived bound of the files design (route: `3 x http_multipart_envelope_max_bytes`, counting the parsed file part, the upload object and core's joined bytes; `Recognize`: `unary_max_encoded_audio_bytes + 6 x 16000 x unary_max_decoded_duration_seconds + 44` bytes plus a 4 MiB slice allowance, counting the encoded request, the decoded `float32` samples, the resampler's slice state and temporaries and the WAV), excluding core's decode memory; at the default configuration a test shall measure each path's peak under 128 MiB, as the increase in `tracemalloc`'s traced peak over the pre-request baseline for one maximal request with core's service replaced by a stub that reads the bytes and returns a transcript.
- [x] **ING-FILE-044**: The samples `Recognize` hands core (the WAV of ING-FE-008, decoded) shall equal the samples the stream side hands `feed` for the same audio after the requantization of ING-FE-012, and the frontend shall send core exactly the locale a stream opened with the same client locale would use (ING-FILE-013, ING-CORE-015).
- [ ] **ING-FILE-056**: For a file whose request ends with EOS and a comparison session that is flushed successfully, with a fixed locale (no `update_locale`), the same samples (ING-FILE-044), a comparison session opened at the cadence core's file path uses (the deployment guide's `num_lookahead_tokens`, ING-EP-058), the same precision settings and endpointing disabled on both, an integration test shall find the file's transcript equal to the session's final transcript; transcript equality is the string projection of the label-sequence equality the model plugin's FILE-ROW-007 states.
- [x] **ING-FILE-057**: A contract test shall build core's `TranscriptionRequest.to_sampling_params` result and fail when it sets a sampling parameter from a request field that the guard does not handle (the fields of ING-FILE-020, the completion limit of ING-FILE-010 and `vllm_xargs` of ING-FILE-024).
- [x] **ING-FILE-058**: A CPU test shall decode the WAV of ING-FE-008 through core's audio decoder and fail unless the decoded samples equal the WAV's 16-bit values divided by 32768.
